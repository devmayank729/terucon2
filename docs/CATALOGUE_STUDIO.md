# Catalogue designs in the Design Studio, and where their pictures live

Written 2026-11-04. Targets: C1 (AI render), A1 (shop), C4 (finder). Everything below is in the website; **nothing under `swatchroom/` was changed** (it is a verbatim copy of your separate project).

## What a visitor gets

1. **In the Design Studio**, when a wall, a door or a piece of furniture is selected, the finish list starts with a group **"Terucon catalogue"**: the 63 SuperBond designs, each card showing the design's real photograph, its name and code (`SB804 · marble-like veining, gloss`). Picking one draws it into the visitor's photo **instantly** in the browser (WebGL2 / WebGPU, the studio's instant preview: section "The instant preview" below, added 2026-11-05) and **Render** sends it to the AI as before, with the design's own photograph as a reference.
2. **In the shop**, the same designs, with pictures read from Cloud Storage and a short description of how each looks.
3. **In TeruBot and the Finder**, the same pictures and descriptions (TeruBot reads the description when it talks about a design).

## Where things are stored (nothing on the web server's disk)

| What | Where | Written by |
|---|---|---|
| Name, printed code, product id (`TIPL-SB804`), dominant colour, page | MongoDB `terucon_catalogue_items` | the catalogue engine (earlier sessions) |
| The 320 px thumbnail of each page | bucket `thumbs/<catalogue>/<itemId>.jpg` | the catalogue engine |
| The 800 px picture of each design | bucket `cards/<catalogue>/<itemId>.jpg`; the record is `shopImage` on the item | `node tools/publish-shop-images.js --apply` (done 2026-11-04: 63 pictures, each read back and compared byte for byte) |
| What Gemini saw in each picture | MongoDB, field `studio` on the item; an export for the shop build: `catalogue/data/superbond-colour-detail.json` | `node tools/describe-designs.js --apply` (done 2026-11-04: 63 of 63) |

`shopImage` and `studio` are fields of their own, **not** inside `images`: the catalogue engine rewrites `images` whenever the PDF is ingested again (`catalogue/terucon_catalogue/mongo.py`, `PUBLISHER_OWNED`) and never touches a field it does not know. A re-ingest therefore keeps both.

The 63 files that used to sit in `media/materials/` (8 MB, copied into every deploy) are gone from the server. `/media/materials/tipl-sb804.jpg` is now answered by `server/routes/catalogueMedia.js`: it finds the design in MongoDB, signs a five-minute address for the object, reads it from Cloud Storage and sends it (`Cache-Control: public, max-age=3600, stale-while-revalidate=86400`, an ETag, 304 on a repeat). The bytes are kept in the server's **memory** only (at most 32 MB, about 12 MB for the whole catalogue), never on disk. Only a design that MongoDB lists is answered (a 404 for any other id), so it is not a way to read the bucket. If the bucket, the signing key or the database does not answer, the shop shows a quiet tile in the design's colour with its code (never cached; header `X-Terucon-Picture: unavailable`) instead of a broken image. Because the address did not change, nothing in the shop, TeruBot or the Finder had to change.

## How a design reaches the studio

```
studio page (signed in)
  loader (site/patches/snippets/studio-loader.js, step "catalogue-loader" of site/patches/studio.json; replaces the studio's one-line loader)
    -> GET /api/catalogue/studio-finishes               designs from MongoDB, each with its brief               (waits at most 4 s)
    -> site/catalogue-ui/studio-finishes.js             adds the group "Terucon catalogue" to the studio's own CATALOG (wall, door, furniture), first in the list
    -> starts /js/swatchroom-app.js                      whatever happened above; with the catalogue off the studio is exactly as before
  while the studio runs: an observer puts the design's photograph on its card (the studio draws cards in code and has no picture type)

a render (the studio's own POST /api/ai/generate)
  -> server/lib/studioReference.js                       in front of the studio's route; sees the marker [[terucon-design:TIPL-SB804]] in the brief
       fetches the design's 800 px picture, adds it to the request as the LAST image, adds four rules (11 to 14) about how to use it to the system prompt,
       adds one line to the brief, removes the marker. Anything missing (design, picture, database): the marker is removed and the render goes ahead on the text alone.
  -> the studio's route -> Gemini (the model chain, retries and key are the studio's, unchanged)
```

Each surface kind gets its own item id (`tipl-sb804` for a wall, `tipl-sb804-door`, `tipl-sb804-furniture`): the studio forgets a selected finish whose kind is not the clicked surface's (`itemFitsKind`), so one id for three kinds would be dropped on a door. **Each item carries a `texture`** (the design's own photograph, `textureOf()` in `server/catalogue/studioFinishes.js`, copied and checked by `site/catalogue-ui/studio-finishes.js`) so the instant preview can draw it. *Until 2026-11-05 they had none* (the note here said a photograph of a sheet is not a tileable texture), which is why the newer finishes could only be rendered by the AI and showed the studio's reason "This finish adds or restyles an object, so it has no instant preview", which was also the wrong sentence for a material.

**Which surfaces?** Wall, door and furniture (cabinet faces): a decorative sheet. Not floor, ceiling or window. That is my choice, nothing in the repo says where the designs may be used; change `STUDIO_KINDS` in `server/catalogue/studioFinishes.js`.

## The prompt

Two parts: the **brief** (what to make) and the **rules** (how to use the photograph). Both are in `server/catalogue/studioFinishes.js`.

* The brief names the design and says, from what Gemini saw in the picture: how it looks, its colours, its pattern, **which way the pattern runs**, **how large the marks are** (fine, medium, large), **how it reflects light** (matte to metallic), **how the surface feels** (flat to embossed), and a short instruction written for an image model (`render`). Without a Gemini description it says the colour and that the pattern and finish are to be taken exactly from the reference photograph.
* The photograph is Image 4 (Image 3 for the lite model, which sends no guide image: the number is counted from the images actually sent). Rules added to the studio's own ten:
  11. reproduce what the photograph shows (colours, the shape, density and direction of the marks, sheen, relief); do not recolour, simplify or invent;
  12. it is a sample, not a picture to paste: no frame, label or text, and **not its lighting**: the room's light decides direction, falloff, shadows and reflections;
  13. scale the pattern from the room (rule 8), never stretch the sample over the surface, never shrink it to noise, no visible repeat or seam;
  14. keep the sheen and relief as the camera would see them at this distance; colour stays true to the photograph after the room's light is applied.

### What Gemini is allowed to write (`tools/describe-designs.js`)

Gemini sees the picture, the printed name and the code, and is told to describe **appearance only**: never what the design is made of, its size or thickness, how it performs, its price or where it should be used, and to ignore the photograph's own lighting. Every answer is checked in code: the fields must be present and in their lists, texts must not be too long, and any text that states a measurement with a unit, a material (laminate, veneer, aluminium, stone species...), a performance (waterproof, fire, scratch...) or a price is refused and asked for again once. A metal named as a colour or a look ("copper-coloured") is allowed; "made of" is not. **The words are not checked for being true**: they say what the picture shows. They appear in the shop as "Written by AI from the catalogue picture: it describes how the design looks." Please read them (`catalogue/data/superbond-colour-detail.json`, all 63).

## The instant preview (WebGL2 / WebGPU) of a design, added 2026-11-05

**You reported:** the newer items cannot be drawn instantly with WebGL, and asked for every item to support both the instant preview and the Gemini render.

**Why it did not work (two causes, both found in the code and then reproduced).**
1. *No texture.* The studio's gate for the instant preview is `canUseFastRender(...)` (`swatchroom/public/js/lib/fastrender/tiers.js`): the finish needs `item.texture.url`. The studio's own finishes get one from a list at start-up (`swatchroom/public/js/data/catalog.js`, `attachTextures`); the catalogue designs are added to the list afterwards by `site/catalogue-ui/studio-finishes.js`, which gave them none, on purpose.
2. *No fit for a door or a piece of furniture.* The preview also needs a 3D fit for the clicked surface, and both sources of one covered only wall, floor and ceiling: the server's plane fit (`swatchroom/server/lib/pipelineRunner.js`) and the browser's outline estimate (`provisional.js`). The designs are offered on **wall, door and furniture**, so on two of the three they could never have been previewed, texture or not. [RAN: the studio's own preview code, given a design's texture on the clinic photo's door, cabinet front and sofa, gives them no slot and paints nothing; on the wall it has a slot.]

**What is built** (the website only; `swatchroom/` is not touched: the changed studio files are served from `site/overlays/studio/`, section 12 of `docs/DESIGN_STUDIO_ARCHITECTURE.md`).
* **The texture.** Each design's `texture` is its own 800 x 1220 photograph (the picture route `/media/materials/<id>.jpg`, read from Cloud Storage), a tile size, and the sheen Gemini read. Nothing to upload or regenerate: the pictures are already in the bucket.
* **The tile size is a guess: 1.22 m wide (a 4 ft sheet), 0.854 m high.** The catalogue records no size for a design (this file said so before). It only decides how large the pattern is on the wall in the preview. **It is named `previewTileWidthM` / `previewTileHeightM`, not `tileWidthM` / `tileHeightM`, on purpose:** the studio quotes `tileWidthM` / `tileHeightM` to the render model as a measured repeat ("Tile repeat scale must match 1.2 m x 0.84 m", `swatchroom/public/js/lib/prompts.js`), and a guessed size must not reach the AI as a fact. A test runs the studio's real `prompts.js` with a design and shows the sentence is not there. One constant to change when Terucon gives the real sheet size: `PREVIEW_TILE_WIDTH_M` in `server/catalogue/studioFinishes.js`.
* **Making a photograph into a repeating tile** (`loadMaterialBitmap` in `site/overlays/studio/js/lib/fastrender/renderer.js`, helpers in `geometry.js`). The tile layer is 640 x 448; a photograph of a sheet is portrait, so the middle 800 x 560 of it is used (it used to be stretched, which squashed every vein to about 0.6 of its height). A photograph is not made to repeat, and its light drifts across the sheet, so every tile border was a step in brightness, which the studio's existing seam repair (`makeSeamless`) turned into a dark grid over the whole wall (seen on the teak and the marble). The fix is to take the slow drift out first (`flattenTone`: each colour channel minus a very blurred copy of itself plus its mean, so the average colour is kept) and then repair the seam as before. A design with **bold features** (Gemini's scale "large": 8 of the 63: SB2004, SB3003, SB621, SB8001, SB8002, SB828, SB830, SB940) asks for a wider blur (`?tone=100` on the picture's address; the route ignores it; the default is 40), because 40 flattened away exactly what makes them look like themselves. **Tried and rejected, in Chrome, on the same designs:** mirroring the tile 2 x 2 (it makes a kaleidoscope of a veined marble), removing only the smooth part of the border mismatch with ramps (washed out the bold designs), and a radius of 150 (leaves a faint grid on the teak). The values (40, 100) were chosen by eye on about six designs; they are not a measured optimum. The studio's own textures are not flattened (only pictures under `/media/` are).
* **A picture that could not be read is never tiled.** The picture route answers a design whose picture it cannot read (no database, no signing key, Cloud Storage away) with status 200 and a small SVG tile that prints the code. The loader refuses it (`X-Terucon-Picture: unavailable`, or any answer that is not a raster picture) and the preview is simply not drawn, so nobody sees a wall of "picture not available".
* **Sheen.** The preview's highlight follows the sheen Gemini read (`matte` / `satin` / `semi-gloss` / `gloss` / `metallic`) instead of guessing from the words of the brief: the brief always says "The surface is flat and smooth" for a flat relief and `flat` is one of the studio's matte words, so a glossy design read as matte.
* **Doors, furniture and "other" objects get an estimate** (`provisional.js`, `ESTIMATED_KINDS`; `previewScene.js` borrows it for them when the room's real fit is there): an upright plane standing on the floor where the object meets it, facing the camera, for a door (when its top edge is level; otherwise a four-corner estimate with an assumed height of 2.1 m), for furniture (0.9 m when there is no floor under it) and for "other" (1 m). That is exact for a door or a cabinet front and a stand-in for a sofa, a bed or a table (the pattern is not foreshortened along a seat or a table top); like every estimate it is flagged, so the studio keeps pointing at Render for the finished picture. **A window is not covered:** its finishes add curtains and blinds in front of it. This also turns the preview on for the studio's own 9 textured furniture finishes (upholstery, wood) and 2 "other" paints, which never had it.
* **Walls first.** The shader holds 16 surfaces; with doors and furniture in the scan a wall could have been pushed out of the preview, so walls, floors and ceilings take their slots first.
* **The studio's sentence for a surface with no fit** now says "Instant preview covers walls, floors, ceilings, doors and furniture. This surface (a window, or one too small to outline) has no fit, so use Render to see the finish." (`previewReason.js`, an overlay copy).
* **Both together.** Picking a design previews it; **Render** is unchanged for the AI (marker, the design's photograph as a reference, rules 11 to 14). The studio adds the instant preview as a perspective guide to the AI render only for a trusted, fitted surface (`shown.kind === "fused"` and a trusted fit, `studio.js`), never for an estimate, so a door or a cabinet (always an estimate) sends no preview to Gemini, and a wall sends one only when the room's real fit is good. For that case rule 13 now says a preview in the guide image is a stand-in: take its convergence and the room's light, never its repeat size or the joins of its tiles (the studio's own sentence tells the model to keep the preview's "repeat scale"). The sentence is added only when the render has a guide image (the reference photograph is Image 4 or later); on the lite model, which sends none, Image 3 *is* the reference photograph and the sentence is left out (a review caught that my first version said "Image 3 may be a preview" there). **That sentence was not run live against Gemini.**

**What cannot have an instant preview, and why.** The preview swaps a *texture* on a *surface*. A finish that adds, removes or restyles an *object* has no texture, so it renders with the AI only. Counted from `swatchroom/public/js/data/catalog.js` (run, 2026-11-05): **36 of the studio's own 103 finishes have no texture** (wall 8: 7 add-an-object items and 1 panel; floor 4: rugs; ceiling 10: 5 false-ceiling styles and 5 lights; window 7: 5 blinds and shutters and 2 frames; door 5: door styles; furniture 1 and other 1: "Remove" edits), and **none of the 63 catalogue designs**. 4 more (the curtains) have a texture but sit on windows, which have no fit. Those stay Render-only; the studio says so in words when one is picked. So "every item supports both" holds for every **material** finish on a wall, floor, ceiling, door, furniture or other surface, and cannot hold for an item that adds or removes an object.
